# NINJAS X — локальный прототип 3v3 MOBA

Репозиторий содержит сайт с регистрацией (`web`), игровой клиент React + Phaser (`client`) и API/Socket.IO сервер (`server`). PostgreSQL хранит аккаунты и героев, Redis обслуживает очередь BullMQ. Состояние проекта — прототип: полноценная серверная симуляция матча ещё не реализована.

## Быстрый старт

Нужны Node.js 22 (версия указана в `.nvmrc`), npm и доступный Docker daemon с Compose. Используйте **npm и `package-lock.json`**; другие lockfile в проект не добавляйте.

```bash
nvm use 22                      # если установлен nvm
bash scripts/setup-local.sh     # npm ci, .env, контейнеры, миграции и seed
npm run dev                     # отдельный терминал
```

Откройте сайт на <http://localhost:5174>. Регистрация/вход находятся в `web`; кнопка запуска переводит в игровой клиент на <http://localhost:5173>. API и `/health` доступны на <http://localhost:3000>. Локальные PostgreSQL и Redis опубликованы на портах `6432` и `7379`. При повторном запуске достаточно `docker compose up -d` и `npm run dev`; подготовительный скрипт можно запускать повторно. Остановить контейнеры: `docker compose down` (тома данных сохраняются).

Конфигурация сервера хранится в игнорируемом Git файле `server/.env`, созданном из `server/.env.example`. В примере только локальные значения. Для общих сред задайте собственные пароль базы и `JWT_SECRET`; секреты не коммитьте. Клиент использует `VITE_SERVER_URL` (по умолчанию `http://localhost:3000`), сайт использует `VITE_CLIENT_URL` (по умолчанию `http://localhost:5173`). При смене портов согласуйте Compose, env, Vite proxy и CORS. Prisma CLI и сервер работают из workspace `server`, поэтому `.env` лежит именно там.

## Команды и проверка

```bash
npm run build                   # TypeScript и production-сборки всех workspace
npm run test:e2e                # Playwright: критический путь в Chromium
npm run db:deploy               # применить существующие миграции
npm run db:seed                 # заполнить каталог героев и способностей
```

Для первого запуска браузерных тестов после установки зависимостей: `npx playwright install chromium`. Тесты требуют подготовленной локальной базы и Redis; Playwright сам запускает API и два Vite-сервера. Успешный сценарий: регистрация → переход из сайта в клиент → авторизованное меню → создание лобби → выбор героя → игровой canvas. Результаты ошибок сохраняются в `test-results/` и `playwright-report/`. Сценарий создаёт аккаунт с уникальным адресом в локальной базе; CI использует одноразовую базу. Локальные тестовые аккаунты пока автоматически не очищаются.

## Устройство проекта

| Путь | Назначение |
| --- | --- |
| `server/src/index.ts`, `server/src/socket.ts` | Express API, Socket.IO, лобби и события матча |
| `server/prisma/` | Схема, миграции и seed |
| `web/src/` | Страницы сайта, авторизация и переход в игру |
| `client/src/App.tsx` | React-поток меню → выбор героя → игра |
| `client/src/scenes/GameScenePhase3.ts` | Phaser-сцена и большая часть игровой логики |

В `web` переход в игру передаёт JWT в URL клиента; клиент забирает его в localStorage и удаляет из адресной строки. Это текущий механизм прототипа, который нужно заменить перед публичным развёртыванием. `server` обрабатывает аутентификацию, лобби, очередь подбора и пересылку входных событий. Значительная часть движения, боя и AI находится в клиенте. Запуск игры из созданного лобби сейчас инициируется клиентом и не является подтверждённым сервером матчем.

Основные HTTP-маршруты: `POST /auth/register`, `POST /auth/login`, `GET /auth/me` (Bearer token), `GET /heroes`, `GET /heroes/:id`, `GET /health`. Основные Socket.IO события: `auth`, `lobby:create`, `lobby:join`, `lobby:leave`, `lobby:ready`, `lobby:kick`, `lobby:list`, `queue:join`, `queue:leave`, `match:found`, `game:input`. Точные payload и обработчики смотрите в `server/src/socket.ts` и `client/src/network/socket.ts`. В игре используются WASD или мышь для перемещения; способности и атаки уточняйте по текущему UI, так как старые подсказки сайта не полностью совпадают с реализацией.

## Подтверждённые ограничения и ближайшие задачи

1. **Авторитет игры и безопасность.** Игровая логика и выбор команды частично работают на клиенте; сервер пересылает `game:input`, но не ведёт полноценную симуляцию. Лобби позволяет локально начать игру без серверного матча. Не считать текущий сетевой код защитой от читов.
2. **Подбор игроков.** Очередь требует шесть игроков; обработчик выхода подтверждает действие, но не удаляет ожидающего игрока из массива worker. Нужны корректная отмена, очистка при отключении и серверный жизненный цикл матча.
3. **Поддерживаемость.** `GameScenePhase3.ts` содержит более 3000 строк. Разделить правила боя, AI, рендеринг и сетевые события после закрепления тестами.
4. **Согласованность интерфейса.** Тексты сайта местами обещают 5v5, три линии или готовые ranked-функции, в то время как текущая цель — 3v3-прототип. Проверять продуктовые заявления по коду.
5. **Секреты и окружение.** Перед публикацией устранить передачу JWT через URL, убрать известные локальные значения из конфигурации развёртывания и добавить проверку обязательных переменных.
6. **Тесты.** Первый Playwright-сценарий проверяет запуск и проход в игру; игровой баланс, репликация, reconnect, производительность и многопользовательский матч пока не покрыты.
7. **Зависимости и размер клиента.** При чистой установке npm сообщил о 25 предупреждениях безопасности; их нужно отдельно разобрать по пакетам и доступным обновлениям. Сборка клиента выдаёт предупреждение о JavaScript chunk размером около 1,74 МБ.

Следующий этап: сначала серверный жизненный цикл матча и очередь, затем декомпозиция сцены с проверками игровых правил. Старые заметки о Go/WebRTC/Lua были идеями для возможного будущего исследования, а не описанием реализованной архитектуры.

# NINJAS X — сетевой аренный прототип

Репозиторий содержит сайт с регистрацией (`web`), игровой клиент React + Phaser (`client`) и API/Socket.IO сервер (`server`). PostgreSQL хранит аккаунты, героев и завершённые матчи; Redis обслуживает BullMQ и контрольные снимки. В сетевой арене можно играть вдвоём или командами до 3v3: сервер считает движение, атаки, способности, здоровье и победу после пяти убийств команды.

## Быстрый старт

Нужны Node.js 22 (версия указана в `.nvmrc`), npm и доступный Docker daemon с Compose. Используйте **npm и `package-lock.json`**; другие lockfile в проект не добавляйте.

```bash
nvm use 22                      # если установлен nvm
bash scripts/setup-local.sh     # npm ci, .env, контейнеры, миграции и seed
npm run dev                     # отдельный терминал
```

Откройте сайт на <http://localhost:5174>. Регистрация/вход находятся в `web`; кнопка запуска переводит в игровой клиент на <http://localhost:5173>. API и `/health` доступны на <http://localhost:3000>. Локальные PostgreSQL и Redis опубликованы на портах `6432` и `7379`. При повторном запуске достаточно `docker compose up -d` и `npm run dev`; подготовительный скрипт можно запускать повторно. Остановить контейнеры: `docker compose down` (тома данных сохраняются).

Конфигурация сервера хранится в игнорируемом Git файле `server/.env`, созданном из `server/.env.example`. В примере только локальные значения. Для общих сред задайте собственные пароль базы и `JWT_SECRET`; секреты не коммитьте. Клиент использует `VITE_SERVER_URL` (по умолчанию `http://localhost:3000`), сайт использует `VITE_CLIENT_URL` (по умолчанию `http://localhost:5173`). При смене портов согласуйте Compose, env, Vite proxy и CORS. Prisma CLI и сервер работают из workspace `server`, поэтому `.env` лежит именно там.

## Команды и проверка

```bash
npm run build                   # TypeScript и production-сборки всех workspace
npm run test:server             # правила игры и запуск собранного match worker
npm run test:e2e                # Playwright: критический путь в Chromium
npm run db:deploy               # применить существующие миграции
npm run db:seed                 # заполнить каталог героев и способностей
```

Для первого запуска браузерных тестов после установки зависимостей: `npx playwright install chromium`. Тесты требуют подготовленной локальной базы и Redis; Playwright сам запускает API и два Vite-сервера. Они проверяют регистрацию, лобби, выбор героя, серверное движение и получение снимков двумя игроками. Результаты ошибок сохраняются в `test-results/` и `playwright-report/`. Сценарии создают аккаунты с уникальными адресами в локальной базе; CI использует одноразовую базу. Локальные тестовые аккаунты пока автоматически не очищаются.

## Устройство проекта

| Путь | Назначение |
| --- | --- |
| `server/src/index.ts`, `server/src/socket.ts` | Express API, Socket.IO, лобби и маршрутизация событий матча |
| `server/src/match/` | Авторитарные правила, отдельный поток матча и управление воркерами |
| `shared/` | Типы и Protobuf-схема бинарного сетевого протокола |
| `server/prisma/` | Схема, миграции и seed |
| `web/src/` | Страницы сайта, авторизация и переход в игру |
| `client/src/App.tsx` | React-поток меню → выбор героя → игра |
| `client/src/scenes/NetworkGameScene.ts` | Отображение серверных снимков, интерполяция и локальное предсказание движения |
| `client/src/scenes/GameScenePhase3.ts` | Старая локальная сцена с отдельной игровой логикой; сетевой матч её не использует |

В `web` переход в игру передаёт JWT во фрагменте URL (`#token=`); браузер сохраняет его в localStorage и убирает из адресной строки. Хост запускает лобби запросом `lobby:start`; сервер создаёт `node:worker_threads` воркер и назначает команды. Клиент отправляет только направление, атаку, выбранную способность и номер ввода. Воркер с частотой 30 тиков/с считает позиции, столкновения, урон, ману, перезарядки и исход боя. Socket.IO рассылает Protobuf-снимки с частотой до 15/с; клиент держит буфер для интерполяции других игроков и плавно сверяет собственную позицию с сервером. Redis хранит метаданные матча и контрольный снимок раз в 30 тиков, PostgreSQL — статистику завершённого матча.

Управление: WASD — движение, Space — базовая атака ближайшего врага, Q и клавиши 1–3 — способности выбранного героя. Герои, их характеристики, стоимость маны и перезарядки загружаются из PostgreSQL. Dash, удар, атака по области, щит/бафф, лечение и воскрешение обрабатываются только сервером; клиент показывает цвет, форму и эффекты героя. Победа наступает после пяти убийств команды. Лобби с одним игроком пригодно для тренировки движения и Dash, но бой в нём завершить невозможно.

Основные HTTP-маршруты: `POST /auth/register`, `POST /auth/login`, `GET /auth/me` (Bearer token), `GET /heroes`, `GET /heroes/:id`, `GET /health`. Основные Socket.IO события: `auth`, `lobby:create`, `lobby:join`, `lobby:leave`, `lobby:ready`, `lobby:kick`, `lobby:list`, `lobby:start`, `queue:join`, `queue:leave`, `match:found`, `match:select-hero`, `game:input`, `game:snapshot`, `match:aborted`. Точные payload и обработчики смотрите в `server/src/socket.ts`, `client/src/network/socket.ts` и `shared/index.d.ts`.

## Подтверждённые ограничения и ближайшие задачи

1. **Объём режима.** Реализована небольшая арена с шестью героями из БД и базовыми эффектами их способностей. Миньоны, башни, AI, полноценная карта и объекты старой сцены не перенесены. Персонажи и анимации нарисованы программно; художественные ассеты и баланс ещё требуют работы. Ограничение в 32 одновременных матча предварительное и не подтверждено нагрузочным тестом.
2. **Надёжность матчей.** При сбое воркера матч прерывается; снимки в Redis пока не используются для восстановления. Переподключение к идущему матчу не реализовано. Выбор героя ограничен двумя минутами, длительность матча — 30 минутами, матч останавливается через 30 секунд после отключения всех участников. Очередь BullMQ требует шесть игроков; ожидающие участники пока держатся в памяти процесса, поэтому рестарт сервера теряет подбор.
3. **Поддерживаемость.** `GameScenePhase3.ts` содержит более 3000 строк, но больше не используется сетевым матчем. Разделять её при переносе оставшихся игровых правил, не вводя искусственного предела строк.
4. **Согласованность интерфейса.** Тексты сайта местами обещают 5v5, три линии или готовые ranked-функции, в то время как текущая цель — 3v3-прототип. Проверять продуктовые заявления по коду.
5. **Секреты и окружение.** Фрагмент URL не отправляется HTTP-серверу, но JWT всё ещё лежит в localStorage. Перед более широким публичным запуском перейти на безопасную серверную сессию, усилить проверки регистрации и защиту от злоупотреблений.
6. **Тесты.** Серверные тесты проверяют движение, бой, способности, Protobuf и работу собранного воркера; Playwright проверяет путь одного и двух игроков, включая Dash. Баланс, устойчивость при потере пакетов, reconnect, восстановление и производительность пока не покрыты.
7. **Зависимости и размер клиента.** После обновления production-зависимостей `npm audit --omit=dev` не сообщает уязвимостей; полный audit всё ещё видит проблемы инструментов разработки. Сборка клиента выдаёт предупреждение о JavaScript chunk размером около 1,75 МБ; нужна дальнейшая разбивка Phaser и UI.

Следующий этап: переподключение к матчу, устойчивый подбор после рестарта и игровая карта с целями. Старые заметки о Go/WebRTC/Lua были идеями для возможного будущего исследования, а не описанием реализованной архитектуры.

## Production и CI/CD

Production-образ из [Dockerfile](Dockerfile) обслуживает сайт `/`, игру `/game/`, API и Socket.IO на одном origin. [compose.prod.yml](compose.prod.yml) запускает PostgreSQL, Redis, миграции, повторяемый seed и приложение; снаружи открыт только `127.0.0.1:13002`. Nginx и Certbot обслуживают `https://ninjas.baibakovkir.space`. DNS A должен указывать на `176.123.163.174`. Локальный образ можно собрать командой `docker build -t ninjas-x:local .`.

GitHub Actions сначала выполняет сборку, серверные тесты и Playwright, затем публикует образ `ghcr.io/baibakovkir/ninjas-x:sha-<commit>` и развёртывает его через SSH. Deploy проверяет `/health` и публичный HTTPS-адрес; при ошибке возвращает предыдущий образ. Миграции БД автоматически назад не откатываются, поэтому несовместимые изменения схемы требуют отдельного плана.

Для первого деплоя нужны GitHub Secrets `VM_SSH_KEY`, `VM_KNOWN_HOSTS`, `VM_USER`, при нестандартном адресе/порте — `VM_HOST`, `VM_PORT`. Скрипт [ops/init-env.sh](ops/init-env.sh) один раз генерирует пароли PostgreSQL и JWT на VPS в `/opt/ninjas-x/.env` с правами владельца; при следующих релизах он сохраняет существующий файл. Образ не содержит секретов. На VPS нужны Docker Compose, Nginx, Certbot, OpenSSL и возможность выполнить `sudo` для настройки сайта. Шаблон значений — [ops/production.env.example](ops/production.env.example); реальные значения в Git не добавляются.

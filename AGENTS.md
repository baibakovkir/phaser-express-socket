# Правила работы агента

Цель — самостоятельно доводить согласованную задачу до проверяемого результата. Читайте `README.md` перед началом работы и проверяйте текущее состояние Git. Обычные обратимые правки, локальный запуск, исследование, тесты и исправление обнаруженных блокеров выполняйте без отдельного запроса разрешения. Если задача неясна, используйте код и документацию как источник фактов, примите локальное решение и объясните его в отчёте. Спрашивайте пользователя только о существенном продуктовом выборе или действии с внешними/необратимыми последствиями.

## Карта и источники истины

- `server/`: Express, Socket.IO, BullMQ, Prisma. Контракт событий проверяйте по `server/src/socket.ts` и `client/src/network/socket.ts`.
- `web/`: регистрация, вход и переход в клиент. `client/`: React оболочка и Phaser сцена.
- `server/prisma/schema.prisma` и миграции — источник истины для базы; `server/.env.example` — локальные переменные; `package-lock.json` — единственный lockfile.
- README описывает фактический запуск и известные ограничения. Обновляйте его при изменении команд, env, портов или пользовательского маршрута. Не отмечайте прототипные функции как готовые без проверки.

## Архитектурные принципы (критически важно)

Это **целевая архитектура для всей игры**. Сетевой режим уже считает движение, столкновения игроков, базовую атаку, способности, ману и здоровье в `server/src/match/` внутри `node:worker_threads`. Старая локальная сцена `client/src/scenes/GameScenePhase3.ts` всё ещё содержит отдельные правила для миньонов, башен и AI; сетевой матч её не запускает. BullMQ `Worker` в `server/src/queue/` обслуживает подбор и не является игровым потоком. Переносите оставшиеся правила на сервер по проверяемым этапам.

1. **Авторитарный сервер.** Node.js сервер — единственный источник истины для координат, движения, попаданий, урона, здоровья, ресурсов, AI и исхода матча. Клиент отправляет намерения игрока (направление, действие, номер/время ввода), отображает серверные снимки и интерполирует их между обновлениями. Сервер проверяет допустимость ввода и не принимает клиентские координаты или результаты боя как факт. Локальное предсказание движения допустимо только как визуальный эффект с последующей сверкой по серверному состоянию.
2. **Изоляция матчей.** Express обслуживает HTTP-маршруты (авторизация, профили, лобби); Socket.IO в основном процессе принимает соединения и передаёт ввод и снимки между клиентами и симуляцией, не выполняя игровой цикл. Для текущей цели один активный матч исполняется в отдельном `node:worker_threads` воркере. Управляющий процесс создаёт и завершает воркер, маршрутизирует сообщения, обрабатывает сбой и ограничивает число одновременных матчей. Один воркер на матч не означает неограниченное создание потоков: проверяйте потребление памяти и CPU перед ростом нагрузки.
3. **Хранение.** Redis хранит очередь матчмейкинга, состав и статус активных матчей, а также контрольные снимки для восстановления и координации. Авторитарное состояние текущего тика находится в памяти воркера; не ставьте Redis-запрос в критический путь каждого движения или удара. После завершения матча подтверждённая статистика и данные аккаунтов сохраняются в PostgreSQL. Отмена очереди и отключение игрока должны реально менять состояние очереди, а не только отправлять подтверждение клиенту.
4. **Простая серверная геометрия.** Для движения, дальности, атак и скиллов используйте детерминированные 2D-проверки: расстояния, окружности и простые хитбоксы. Не добавляйте тяжёлый физический движок без измеренной потребности. Phaser Physics может служить для визуальных эффектов, но не решает исход сетевого боя.

При работе над игровым кодом проверяйте серверные правила без браузера на фиксированных входах и последовательности тиков; Playwright оставляйте для проверки пользовательского пути и синхронизации отображения. Если меняется контракт ввода или снимка, обновляйте обе стороны и тесты в одной задаче.

## Форматирование и организация кода

- **Форматируйте автоматически, когда инструмент настроен.** Выбранный форматтер, его версия и настройки должны быть закреплены в репозитории; проверка форматирования должна запускаться в CI. Сейчас форматтера в проекте нет, поэтому не заявляйте о прохождении такой проверки и не переформатируйте большие файлы ради локальной правки. При добавлении Prettier отделяйте форматирование от ESLint: первый отвечает за внешний вид кода, второй — за качество и возможные ошибки. [Установка Prettier](https://prettier.io/docs/install.html), [совместная работа с линтерами](https://prettier.io/docs/integrating-with-linters/).
- **Сохраняйте единообразие.** Для новых TypeScript/TSX-файлов используйте два пробела, LF, завершающий перевод строки и отсутствие пробелов в конце строк; внутри существующего файла придерживайтесь принятого там стиля кавычек и точек с запятой до ввода общей конфигурации. При настройке Prettier используйте `printWidth` как ориентир для переноса строк, а не жёсткий предел длины строки. Исключайте сгенерированные файлы из форматирования. [EditorConfig](https://spec.editorconfig.org/), [настройки Prettier](https://prettier.io/docs/options), [игнорирование файлов](https://prettier.io/docs/ignore).
- **Делайте структуру читаемой.** Размещайте импорты перед реализацией, группируйте внешние и локальные зависимости, используйте `import type` для импортов только типов. Давайте файлам, экспортам и функциям имена по назначению; комментариями объясняйте неочевидные решения, а не повторяйте код. Не оставляйте неиспользуемые импорты и переменные. [Руководство Google по TypeScript](https://google.github.io/styleguide/tsguide.html), [правило для импортов типов](https://typescript-eslint.io/rules/consistent-type-imports/).
- **Разделяйте по ответственности.** Выносите модуль, когда в файле смешиваются независимые правила, сетевой протокол, состояние, рендеринг и UI или когда изменение одной части вынуждает затрагивать несвязанные части. Файл не должен объединять много игровых задач; новые сетевые правила проектируйте отдельно и постепенно переносите связанную логику из сцены. Избегайте круговых зависимостей и нескольких владельцев состояния матча. Число строк — сигнал для проверки структуры, а не критерий качества само по себе.

## Рабочий цикл

1. Посмотрите `git status --short`, нужные файлы и действующие скрипты. Сохраняйте изменения пользователя; не удаляйте и не сбрасывайте их для удобства установки.
2. Внесите минимальные связанные правки с соблюдением правил форматирования и разделения файлов. Если найден блокер согласованного сценария, исправьте его и сообщите почему. Не расширяйте задачу до переписывания игры без необходимости.
3. Выполните `npm run build`. Для изменений сайта, клиента, авторизации, Socket.IO или локального запуска выполните `npm run test:e2e` с Playwright и проверьте браузерный результат, включая ошибки консоли и запросов. Для серверных правок дополнительно проверьте `/health` и затронутый API/событие.
4. При изменении Prisma добавьте миграцию и проверьте её на локальной базе; не используйте `prisma db push` вместо миграции. Seed должен оставаться повторяемым.
5. В финальном отчёте кратко укажите что изменено, какие проверки прошли, что не удалось проверить и какие ограничения остались. Не называйте сборку или браузерный тест успешными без фактического запуска.

## Границы автономности

Можно самостоятельно редактировать код и документы, устанавливать зависимости, запускать локальные контейнеры и тесты, исправлять проблемы чистой установки. Не отправляйте секреты, не публикуйте проект, не удаляйте пользовательские данные и не выполняйте необратимые операции вне локального тестового окружения без явного разрешения. При недоступности Docker или браузера завершайте остальные проверки и точно указывайте блокирующее условие.
